# v310.1 — production pre-image of the rows the release repairs

**This is not a `.production.grade` file and no gate reads it.** The grade files in
this directory are the output of `verify-deployment.sh --emit-sql`, and the README
here describes that ceremony. This artifact exists for a different reason.

v310.1's deploy manifest records that its row repair has **no automatic reversal**:
the migration sets `proposal_versions.tenant_id` from the parent proposal, and once
that is done the prior value is gone. Reversing it requires knowing what the rows
held beforehand. That is what this file preserves, captured before deployment
rather than reconstructed after it.

It holds identifiers and tenancy only — no proposal content, no customer data, no
credentials, no connection string.

## Reversal

If the row repair must be undone, the pre-image is uniform, so one bounded
statement restores it. It names the five identities explicitly so it can never
touch a row this release did not:

```sql
update public.proposal_versions
   set tenant_id = '72301f45-f07d-4e42-a4d0-fe149ae9ec17'::uuid
 where id in ('1866f1cf-1934-4c69-82f5-d9b37db04a05',
              '4cf1ee3e-8812-4d27-8454-bb1b0c8f6419',
              '6a7600a6-70af-4b19-afe8-8557ae1e8f65',
              'd9dfdf08-46c6-43a5-8296-6dcf97507918',
              '22aa31d4-ee99-4c54-b024-38b9c155feda');
```

This is recorded for completeness, not recommended. Restoring it re-creates the
tenant-isolation defect: it returns five rows to a tenancy their parent proposal
does not share, where RLS will show them to the wrong tenant and hide them from
the right one. Reversal of the three column defaults is separate and independent —
setting them back to the literal UUID — and is described in the deploy manifest.

## Validity

This pre-image describes production as at the capture time above. If production
changes before v310.1 is deployed, re-capture it. The row set is defined by the
predicate `pv.tenant_id is distinct from pr.tenant_id`, so a newly mismatched row
appearing after capture would be repaired by the migration without appearing here.
